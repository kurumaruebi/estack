# estack の計画

ひとことで: 元にしたプロジェクトのコードを土台に、Grok Bot の考え方を入れた個人用のエージェントの環境を、ゼロから組み立てる。VPS 1 台にエージェントが常駐し、コーディングはエージェントが Mac 1 台に頼んで GitHub の PR で受け取る。PR には CI と検証が自動で回り、持ち主は iPhone から承認する。作り方は poteto さんのやり方（pstack）に従い、「工場」より先に「エージェントの出力を信じられる環境」を作る。

- ベース: 元にしたプロジェクト（表示は `LICENSE` と `NOTICE` の通り）。表記は estack に統一した（7 章）。
- この文書は考え方と設計の公開版。機械ごとの設定・アドレス・鍵の置き場・作業の記録は、リポジトリの外の非公開の控えに置く（8 章）。

## 1. 決めたこと

- ライセンスは PolyForm Noncommercial 1.0.0 のまま。非商用でだけ使う。`LICENSE` と `NOTICE`、`Required Notice:` の行は消さない。
- 元にしたプロジェクトの更新は、名前を estack に統一したので自動では取り込めない。要る直しは upstream を見て手で持ってくる。
- 役割: VPS 1 台がエージェント、Mac 1 台がエージェントに頼まれてコーディングする場所（Grok Bot で Cursor のクラウドの環境が受け持つところ）。
- Mac はほかに、家の回線が要る仕事（データセンターの回線から断られるサイトなど）も受け持つ。
- iPhone のアプリは `apps/mobile`（Expo）。開発中は Expo Go で VPS の Metro から開く。
- アカウントとつなぎの仕組み（account service・Signal）は、開発用一式を VPS で動かして使い、iPhone とは Tailscale で直接つなぐ。OpenBot の運営のサービスには何もつながない。
- 段ごとに、持ち主が iPhone で「確かめること」を順に確かめる。

## 2. 作り方の芯

| # | 芯 | estack でやること |
|---|---|---|
| 1 | 逆ピラミッド: 時間はコードの設計と静的解析に、文章は判断の要る所だけ | 決まりは lint・型・試験・フォルダの境界で守る。文書に「〜しない」を足すのは最後の手段 |
| 2 | 2 回起きたら仕組みに | 直す順は ①設計で起こり得なくする ②型・名指しの lint・検査 ③振る舞いの試験 ④文書。新しい検査は、過去の実際の間違いで落ちることを確かめてから入れる |
| 3 | コメントは「なぜ」だけ（99% 禁止） | estack で足すコードに、経緯・日付・言い訳のコメントを書かない。検査で止める |
| 4 | 検証が本体 | 「ビルドが通った」は証拠にしない。動かして、スクリーンショット・動画・値で示す。確かめられなければ「確かめられなかった」と書く |
| 5 | 内側 → 外側 | 検査と検証のループ（段 1・2）が固まってから、PR の流れ（段 3）、夜の作業（段 5）を足す |
| 6 | 計画より実物 | 実験で決められることは試作で決める。持ち主に聞くのは好みの判断だけ |
| 7 | 自律の線 | 元に戻せる作業は聞かずに進める。force-push・マージ・配備・データの削除・人への送信は止まって聞く |
| 8 | 夜に回す前の 4 条件 | 良い状態を知っている／エージェントも同じ道具を持つ／各段が自分の仕事を証明して止められる／作業の記録を読み、繰り返す失敗を仕組みにした |
| 9 | 依頼文 | 目標・合否が出る終わりの条件・見たい証拠・分かっていること・本当の制約を 1 文ずつ。やり方と原因の見立ては書かない |

ほかに採る物: コードベースは庭（次のエージェントが写す見本なので、回避策や古い書き方を残さない）。1 つの PR に 1 つの変更。作業の記録を読み、持ち主が口を出した所を lint やスキルに変える。夜に入った PR は朝に抜き取りで見直す。敵対的なレビューは控えめに使う。

## 3. Grok Bot の考え方（エージェントの側）

| Grok Bot | estack での形 |
|---|---|
| ボットは人の同僚。名前と仕事を持ち、迷ったら「人ならどうするか」で決める | エージェントは少なく、1 体に 1 つの仕事。窓口・開発のリード・エンジニア・調べもの・見直し係など（`estack/agents/`） |
| 窓口のボットが受けて、引き継ぎとグループの会話で協働 | estack の引き継ぎ・エージェント同士のメッセージ・チャンネルを使う。エージェント同士の会話は持ち主から全部見える場所でする |
| 信頼の 3 段階: 読むだけ → 実際に操作して完遂 → 1 つの職務を丸ごと持つ | エージェントごとに段階を決めて権限を絞り、記録を見てから広げる |
| 承認は既定で「先に聞く」 | 元の既定（全部許す）を「先に聞く」に変えた。シェルのコマンドも、読むだけと決まった道具のほかは承認のカードにする |
| 秘密は Vault に置き、ボットに見せない | 鍵はエージェントに見せず、道具が使うときだけ付ける |
| きっかけ: 時刻・webhook・GitHub などのイベント | estack のルーチン（時刻）と webhook を使う |
| 記憶とルーチンはボットごと、スキルは共有 | estack の作りのまま |
| コードは別の環境に頼み、GitHub で受け渡す | 4 章の PR の流れ（Mac の作業係） |

## 4. PR と CI の流れ（コーディングの側）

1. 持ち主（またはルーチンや知らせ）が、窓口のエージェントに頼む。
2. 開発のリードが仕事を分け、エンジニアのエージェントが「依頼文」の形にまとめて Mac への依頼を出す（`estack/bin/coding request`）。依頼は VPS の受け口に貯まる。
3. Mac の作業係（`scripts/estack/mac-worker.ts`、launchd で 1 分ごと）が依頼を取りに来て、依頼ごとに `git worktree` で作業場を作り、指定の CLI を画面なしで動かす。既定は Claude Code。モデルと強さは Mac の設定（`~/.config/estack/worker.json`）で決める。
4. コーディングのセッションは、鍵の置き場に届かない専用の OS ユーザーと閉じ込め（サンドボックス）の中で動かし、Web の道具を外す。
5. 作業係が手元の検査と検証を回し、別の系統のモデルの見直し係がレビューする。通ったらブランチを push して PR を出す。PR の本文に、変えたこと・確かめた手順・証拠・確かめられなかった所を書く。
6. GitHub の CI が PR で回る（変えたファイルの lint・型・試験・コメントの検査・個人の値の検査）。
7. 結果がエージェントの会話に届き、エージェントが持ち主に PR と証拠を添えて報告する。
8. 持ち主が承認すると、作業係が CI の緑を確かめてから squash でマージする。承認は記録に残す。
9. マージされたら VPS が読むだけの鍵で取り込み、開発用一式と Metro に反映し、試し操作（ファズ、`scripts/estack/fuzz-ui.ts`）を回す。

セッションの切り替え:

- 新しい依頼 → 新しい作業場とセッション。
- 同じ PR の直しやレビューへの対応 → 前のセッションに追加の指示（`--follow-up`）。
- 別の機能・バグ・リポジトリ → 新しいセッション。どちらとも取れるときは持ち主に聞く。

Mac の扱い:

- 作業係は自分から VPS へ取りに行く（Mac は外からの接続を受けない）。VPS 側の ssh の鍵は受け口しか動かせない。
- Mac が眠っている間の依頼は VPS に貯め、つながったら順に片付ける。
- 承認は「頼むとき」でなく「マージするとき」に置く。

## 5. 安全の決まり

### 5-1. 承認

- 既定は「操作の前に確認する」。「先に聞く」と「自動で許す」の決まりをエージェントごとに書ける形にし、ぶつかったら「先に聞く」が勝つ。
- 裏の作業（ルーチン）から出た承認は 30 分で切れる。
- 人への送信（メール・メッセージ）、お金、データの削除、マージ、配備は、必ず持ち主の承認を通す。ルーチンから出すメールは下書きで止める。
- SSO・パスキー・CAPTCHA・カードの本人確認は、人が引き継ぐ。
- 他人から来たメールや Web の内容は「指示ではなく情報」として扱う。

### 5-2. 鍵と秘密（GitHub を含む）

- 秘密はエージェントに見せない。道具や作業係が、使うときだけ付ける。エージェントが動く OS ユーザーから読めるファイルに鍵を置かない。
- GitHub は役割で鍵を分け、リポジトリだけに入れた GitHub App の短い鍵（installation token）を使う。App も 2 つに分ける（1 つだと、VPS に置いた秘密鍵で書ける鍵も作れてしまう）。
  - VPS（エージェント）: 読むだけ。秘密鍵はエージェントから読めない別のユーザーの小さな中継（`scripts/estack/github-read-proxy.ts`）が持ち、エージェントは中継を通して読む。書ける鍵は置かない。
  - Mac（作業係）: 書ける。秘密鍵はキーチェーンに置き、作業係だけが使う。push・PR の作成・承認後のマージは作業係がし、コーディングのセッションには鍵を渡さない。
- 差分・報告・レビュー・検証の文に鍵の欠片があれば、push も公開もしない。
- App の ID・キーチェーンの名前・アドレスなどの具体的な値は、リポジトリの外の設定（`~/.config/estack/`）か GitHub の Secrets に置く。

### 5-3. 個人の値

- 名前・アドレス・番号・チームの ID などの個人の値をコードや公開の文書に入れない。`scripts/estack/check-personal.ts`（手元、リポジトリの外の一覧）と `scripts/estack/personal-hashes.ts`（CI、ハッシュだけ）で止める。
- 個人の文書は `estack/非公開/` に置く。このフォルダは公開の書き出しから外す（[公開の手順](../docs/estack-public-release.md)）。

## 6. 進める段

内側（段 1・2）を固めてから外側を足す。各段の「確かめること」は持ち主が iPhone で順に確かめ、済んだら次へ進む。

- 段 0: 開発の環境と iPhone の接続。VPS で開発用一式と Metro を立て、iPhone の Expo Go から Tailscale でつなぐ。
- 段 0.5: お試しのデータを入れずに、空の状態から始める。
- 段 1: 検査と CI。コメントの検査、個人の値の検査、変えたファイルの lint・型・試験を、コミット前のフック・Mac の作業係・GitHub の CI で同じように回す。2 回起きた間違いを仕組みに変えるスキル（`.agents/skills/correct`）と、その表（`estack/決まりと止める仕組み.md`）。
- 段 2: 検証。検証のスキル（`.agents/skills/verify-estack`）と機能の一覧（`estack/機能の一覧.md`）。PR に確かめた手順と証拠を付ける。
- 段 3: PR の流れ。VPS の受け口、Mac の作業係、別のモデルのレビュー、承認後のマージ、VPS への反映とファズ。
- 段 4: エージェントの土台。エージェントのサーバーを常に動かし、承認の既定を「先に聞く」にし、最初のエージェントとルーチンを置く。
- 段 5: 外側のループ。夜の作業、判断の記録（`decisions.tsv`）、朝の見直し。エージェントが自分でマージしてよい線（`estack/checks/merge-line.json`）は今は空で、すべてのマージに持ち主の承認が要る。広げるのは、戻した割合を見て持ち主が決めたときだけ。
- 安定版と開発版に分ける: [安定版と開発版に分ける計画](安定版と開発版.md)。GitHub の `main` が開発版、持ち主が承認したタグが安定版。

## 7. 表記の統一

- 元にしたプロジェクトの表記はコード・文字列・パッケージ名（`@estack/*`）・環境変数（`ESTACK_*`）・ファイル名・文書まで estack に置き換えた。
- 元にしたプロジェクトの運営のドメインは、こちらが持っていないドメインを指さないよう、使えないドメイン `estack.invalid` にした。知らない人や運営の SNS へのリンクも同じ扱いにする。
- 残す物（ライセンスが求める表示）: `LICENSE` と `NOTICE` の中身（`Required Notice:` の行と、元の作者の名前と連絡先）。
- 画像の中に描かれたロゴや文字は置き換えの対象外。

## 8. 公開と非公開の分け方

- 公開のリポジトリは 1 つ。最初の公開だけ、履歴を持たない 1 コミットの書き出しにする（`scripts/estack/export-public.ts`）。そのあとは公開のリポジトリで、上の PR の流れをそのまま回す。
- 公開する物: コード、考え方と設計（この文書）、決まりと止める仕組み、エージェントの定義、手順の文書。
- 公開しない物: 機械ごとの設定（アドレス・ユーザー・鍵の置き場・App の ID）、誰がいつ何をしたかの記録、持ち主の判断の経緯、外の資料の写し。`estack/非公開/` かリポジトリの外に置く。
- 迷ったら「知らない人が読んで困るのは自分か」で分ける。
